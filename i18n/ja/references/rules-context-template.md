## Bootstrap（シナリオ2のみ）

ユーザーが**機能拡張**または**リビジョンモード**に入るが`.product-context.md`がない場合、モードのS1の前に「ステップ0」を挿入。

**プレゼンテーション**：
```
📦 このプロジェクトでプロダクト企画ツールを使用するのは今回が初めてです。その後のフローをより効率的にするため、
まず基本的なプロダクト情報を収集します（約2-3分）。自動的に保存され、今後のセッションで利用できます。
```

### 段階的収集（すべての質問を一度にしない）

**ラウンド1（すべてのモードで必須）**：
- プロダクト名は？
- 一文で何をするか説明してください。
- プロダクトタイプは？（B2C / B2B / B2B2C / 社内ツール）

**ラウンド2（機能拡張で必須、リビジョンではオプション）**：
- 使用している技術スタックは？（言語、フレームワーク、データベース、インフラ）
- キーモジュールまたはサービスは？

**ラウンド3（リビジョンで必須、機能拡張ではオプション）**：
- DAU/MAUまたはリテンション率のデータはありますか？
- 最も一般的なユーザーフィードバックや不満は？
- 既知のセキュリティ問題や技術的負債はありますか？

### 技術スタック自動検出

Bootstrap は**プロジェクトファイルを読み取って**検出を支援できます（読み取りのみ — ハードゲートには違反しない）：

| ファイル | 検出内容 |
|------|------------------|
| `package.json` | Node.jsエコシステム、フレームワーク、依存関係 |
| `Cargo.toml` | Rust |
| `go.mod` | Go |
| `requirements.txt` / `pyproject.toml` | Python |
| `Dockerfile` / `docker-compose.yml` | コンテナ化アーキテクチャ |
| プロジェクトルートディレクトリ構造（`src/`、`app/`、`lib/`など） | モジュール推論 |

確認スタイル：
```
プロジェクトが使用しているものを検出しました：
- 技術スタック：Next.js 14 + TypeScript + PostgreSQL + Redis
- キーモジュール：auth/、billing/、dashboard/、api/
これで正しいですか？追加や修正はありますか？
```

ユーザーが確認した後にのみ書き込み。

### Bootstrap → S1 の順序（Hard Gate — Bootstrap はフローを停止しない）

- **デフォルト動作**：Bootstrap と S1 は**同じターン**内で S0 → S1 の順に実行する必要があります。停止点は **S1 完了後**に固定され、S0/S1 の間ではありません。
- **ユーザーメッセージで必要なフィールドがすでに提供されている場合** → 既知フィールドを表で確認するだけにとどめ、直接 S1 に進む。
- **一部フィールドが欠けている場合** → Bootstrap は**同じターン内で**既知／未収集フィールドを表で提示し、その後**即座に S1 に進む**。未確認フィールドにはプレースホルダーを使用し、未収集フィールドは **S1 確認質問の一部**としてまとめて回答してもらう。
- **禁止事項**：S0 と S1 の間に停止点を入れること。応答内で S1 がまだ `⬜ pending` のままフローがユーザー入力待ちで止まっている場合、このルール違反とみなされます。

Bootstrap 完了後：`.product-context.md` に書き込み（プレースホルダーがあっても先に baseline を書き込む）、同じターン内で S1 に進む。

## 部分的コンテキスト UX（シナリオ3）

```
📦 過去[N]回の企画セッションの記録があります：
- 技術スタック：[Decision Historyからマージした既知のスタック]
- 過去に修正したモジュール：[Decision Historyからマージした影響モジュール]
- コアプロダクト戦略はまだ記録されていません。

どうしますか？
  1️⃣ 直接開始（既知情報を使用、戦略セクションをスキップ）
  2️⃣ まず戦略情報を記入（JTBD、ポジショニング、North Star Metric）
  3️⃣ この情報は正しくない — 修正させてください
```

**自動再構築の試み**：すべての Decision History エントリをスキャンし、`影響モジュール`、`スコープ`、`主要決定`から繰り返し登場するプロダクト名、技術スタック、モジュール名を抽出し、`Architecture & Tech Stack`に自動記入。`<!-- inferred from decision history -->`でマーク。

## コンフリクト UX（コードベース vs コンテキスト）

```
⚠️ 不一致が検出されました：
- コンテキストの記録：[コンテキストからの値]
- プロジェクトコードベース：[コードから検出された値]
どちらが正しいですか？
  1️⃣ コードベースを正とする（コンテキストを更新）
  2️⃣ コンテキストを正とする（移行中の可能性）
  3️⃣ 両方とも不完全 — 説明させてください
```

- **自動上書きしない** — ユーザーに判断を委ねる
- 「移行中」が選択された場合、Architecture セクションに注記：`[移行中] React → Vue 3`
- コンフリクトを Decision History に記録
