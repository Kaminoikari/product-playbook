# フェーズ1：ディスカバリー — JTBD分析

## 1.3 JTBD（Jobs to Be Done）分析

> "分析の単位は消費者ではなく、消費者が達成しようとしているジョブである。" — Clayton Christensen

**JTBD 三層カバレッジ(Hard Gate — 三層すべて必須):**

すべての JTBD 分析は**三層を明示的に網羅**する必要があります:**Functional**(完了するタスク)、**Emotional**(過程中/完了後にどう感じたいか)、**Social**(他者にどう見られたいか)。Functional 層だけを生成するのは JTBD で最も一般的な失敗です — Emotional と Social Job が実際の切替えトリガーであることが多く、B2B では特にそうです。もしあるペルソナが製品に対して本当に Emotional または Social Job を持たない場合は、暗黙の省略ではなく一文で理由を明示してください。

**JTBD 標準構文（Hard Gate — 三節構造を強制）：**

すべての JTBD 文（Primary、Functional、Emotional、Social のいずれの層も）は、**「〜のとき、〜したい、それによって〜」** の三節構造で書く必要があります。三つの節のいずれが欠けても不可：

```
[状況] のとき、[動機・ジョブ] したい、それによって [成果・感情] を得る。
```

英語出力では対応する標準構文を使用：
```
When [situation], I want to [motivation], so [outcome].
```

**不合格例**（表セル内に断片的な記述だけで節構造が欠落）：
- ❌ 「要点を素早くメモする」（When が欠落；so が欠落）
- ❌ 「通勤中に思いついたら記録する」（I want to が欠落；so outcome が欠落）

**合格例**（三節がすべて揃っている）：
- ✅ 「**記事を読み終えて要点がまだ頭に残っているとき**、5秒で最も価値あるインサイトを 1 件記録**したい**。**それによって**数週間後でも見つけ出して新しいアイデアにつなげられる。」

例：住宅ローンの選択肢を比較中の初めてのマイホーム購入者が、**銀行に連絡できない深夜**に月々の支払額を**素早く見積もりたい**、**それによって**パートナーに資金計画を説明できる。

**JTBD 4タイプ分析表：**

各セル（ペルソナ1 / ペルソナ2）には完全な三節構造の JTBD を記入してください。**「自分のために頑張れていると感じたい」「毎日ワークアウトを記録する」「進捗を簡単に追跡する」のような短いフレーズはすべて Hard Gate に FAIL します。** 以下のワークアップ例を文字通りの型として使用してください — 各セルは `When …, I want to …, so …` の文として読める必要があります。

ワークアップ例（B2C フィットネス習慣トラッカー、単一ペルソナ — すべてのセルでこの型を再現すること）：

| JTBDタイプ | 定義 | ペルソナ：多忙なプロフェッショナル |
|-----------|------------|-----------|
| 機能的ジョブ | 特定のタスクを完了する、または機能的な目標を達成する | **長い仕事を終えて帰宅し、次の予定まで20分あるとき**、たった今やったワークアウトを記録し、次に何が推奨されるかを見**たい**。**それによって**計画に頭を使わずにストリークを維持できる。 |
| 感情的ジョブ | どう感じるか、どう感じたいか | **予定していたワークアウトを2日続けて逃したとき**、最初からやり直すのではなく、まだ軌道に乗っていると感じ**たい**。**それによって**継続を台無しにするオールオアナッシングのスパイラルに陥らずに済む。 |
| 社会的ジョブ | 他者からどう見られたいか | **友人にトレーニングの調子を聞かれたとき**、最近の活動のきれいな記録を見せ**たい**。**それによって**自分との約束をやり遂げる人物として見られる。 |
| ジョブコンテキスト | どんな状況でこのジョブを達成する必要があるか | **週を通してスケジュールが不安定なとき（早朝のミーティング、夜の電話）**、どこに収まろうと15〜45分の枠にワークアウトを組み込み**たい**。**それによって**トレーニングが生活と競合するのではなく、生活に適応する。 |

空の表（各セルを完全な `When …, I want to …, so …` 文で埋める — フレーズに短縮しないこと）：

```
| JTBDタイプ | 定義 | ペルソナ1（「〜のとき／〜したい／それによって〜」の完全文を必須） | ペルソナ2（同左） |
|-----------|------------|-----------|-----------|
| 機能的ジョブ | 特定のタスクを完了する、または機能的な目標を達成する | | |
| 感情的ジョブ | どう感じたいか、どんな気持ちになりたいか | | |
| 社会的ジョブ | 他者からどう見られたいか | | |
| ジョブコンテキスト | どんな状況でこのジョブを達成する必要があるか | | |
```

**JTBD深掘り5つの質問：**
1. **根本的な問題**：ユーザーが表面的に述べるニーズの背後にある、本当に解決しようとしていることは何か？
2. **現在の制約**：どんなソリューションが特定の制約により排除されたか？
3. **現在のワークアラウンド**：ユーザーは現在どう対処しているか？どんな回避策を構築したか？
4. **ギャップ**：現在のワークアラウンドのどこが不十分か？（このギャップがあなたの機会）
5. **理想のソリューション**：制約が取り除かれた場合、ユーザーの理想のソリューションはどんなものか？

**Teresa Torresユーザーインタビューベストプラクティス：**
- ユーザーの**実際の過去の行動**にフォーカスし、仮定的な将来の行動ではない
- 「この問題に最後に直面した時、どうしましたか？」と聞く。「どんな機能が欲しいですか？」ではない
- 最もよくある間違い：仮定的な質問をする、ソリューションバイアスを持ち込む、詳細を掘り下げない

### 📝 JTBD品質チェックリスト

ClaudeはJTBD出力後にセルフチェックを行う必要があります（各項目に✅または❌を付け、❌の項目には改善方法を記載）：
- [ ] 機能的 / 感情的 / 社会的の**三層すべて**が「〜のとき／〜したい／それによって〜」（英語では "When ... I want to ... so ..."）の完全な三節構造で書かれているか？（いずれかの層で節が欠けていれば ❌）
- [ ] 具体的なコンテキストが含まれているか？（「いつでもどこでも」ではなく、「銀行に連絡できない深夜に」）
- [ ] 単一のコアジョブにフォーカスしているか？（3つのジョブを1文に詰め込んでいないか）
- [ ] 「このソリューションは本当にこのジョブに対応しているか？」の評価に使えるか？
- [ ] 「現在のワークアラウンド」と「ギャップ」が含まれているか？（ギャップ＝機会）
- [ ] 深掘り質問の Q5 は**標準語彙から少なくとも1つを明示的に使用しているか**(`fear`、`anxiety`、`shame`、`worry`、`dread`、`self-doubt`、`sense of loss`、`threat to identity`、`embarrassment`、`guilt`)?「信頼性が損なわれる」「評判が下がる」のような結果的言い換えはこの項目に FAIL — それらは結果であり感じられた感情ではない。

**実行ルール（Hard Gate）：**
- 各項目に必ず✅または❌を付ける — 空白の[ ]や説明のない✅リストは不可
- **チェックリストには必ず 1 つ以上の ❌ が必要**（`references/rules-quality-review.md` 「強制批判」ルール参照）。⚠️ 警告マークは ❌ の代わりにならず、チェックリスト外の「最も弱い部分」備考も ❌ の代わりにならない。徹底的に見直しても全項目合格と感じる場合は基準を下げて再審査し、❌ を付けるべき項目を 1 つ見つけて補強方法を明記する
- ❌ よくある問題：三節構造の欠落（When / I want to / so のいずれかが欠ける）、抽象的すぎる、複数のジョブが統合されている、コンテキストが欠落、プロダクト機能をジョブの記述に置き換えている、Q5が機能レベルにとどまっている

### 🏢 B2Bプロダクト深掘り要件(Hard Gate)

**Hard Gate — すべての B2B(B2B2C 含む)プロダクトについて、以下の 3 つの下位分析はすべて必須。ユーザーが明示的に要求していなくても、いずれかを省略すると contract failure。** プロダクトタイプが不明確な場合は、まず 1 つ確認質問をしてください — 暗黙のうちに B2C を仮定しないこと。

#### 組織レベルのジョブ分析(Hard Gate — 少なくとも 2 レベルをカバー)

B2B JTBD 分析が個別ユーザーレベルのみに留まる場合、このゲートに FAIL します。組織レベルの Job(コンプライアンス監査、部門横断承認ワークフロー、コスト管理、人材ポリシーアラインメント、監査証跡の完全性)は、いかなる個別ユーザーの日常タスクをも超えたニーズであり、B2B 切替え決定で支配的になることが日常茶飯事です。以下の表は必ず生成し、3 レベルのうち少なくとも 2 つに B2B 固有の Job(漠然とした生産性ステートメントではない)を含める必要があります。

| レベル | 説明 | 例 |
|-------|-------------|----------|
| **戦略的ジョブ** | 組織/経営レベルの部門横断的ニーズ | コンプライアンス監査、コスト管理、人材最適化 |
| **運用的ジョブ** | プロセス/部門マネージャーレベルの調整ニーズ | 承認ワークフロー管理、チーム間情報同期 |
| **タスクジョブ** | 個々のユーザーの日常業務ニーズ | フォーム記入、ステータス確認、レポート出力 |

#### 購入者(Buyer)vs ユーザー(User)分析(Hard Gate)

B2B プロダクトの購入者(契約締結、予算管理)と日常ユーザー(毎日プロダクトに触れる)は、ほぼ常に 2 つの役割、**異なる Job に対応**しています。これらを単一ペルソナとして扱うことは B2B ディスカバリーで最も一般的な失敗です。Hard Gate ルール:

- buyer ≠ user の場合(B2B のデフォルト想定)、**2 つの別個のペルソナ+JTBD ブロック**を生成:1 つは Buyer 用(ROI 正当化、リスク低減、コンプライアンス、ベンダー統合、監査準備)、1 つは User 用(効率、エラー削減、日常使用コンテキスト)。さらにクロスリンク:Buyer の Job が User の Job にどこで依存するかをメモ(例:「Buyer のコンプライアンス Job は、月末まとめ記入ではなく、User が毎週本当に記入することに依存」)。
- buyer = user の場合(例外的 — 創業者主導のツールなど)、なぜこの特定のシナリオで意思決定者が日常ユーザーでもあるのかを一文で明示 — 暗黙的に仮定しないこと。
- 不合格例:1 つのペルソナ(「HR マネージャー」)のみを生成し、予算決定権と日常的なフォーム記入を 1 つの曖昧なアーキタイプに押し込める。これは 2 つの異なる Job を 1 つの漠然とした役割に潰し、分析が製品決定を駆動できなくなる。

#### 深掘り5つの質問 — B2B強化版(Hard Gate)

**Hard Gate — Q5 は次の標準語彙リストから少なくとも1つを明示的に使用する必要があります**:`fear`(恐怖)、`anxiety`(不安)、`shame`(恥)、`worry`(心配)、`dread`(畏怖)、`self-doubt`(自己疑念)、`sense of loss`(喪失感)、`threat to identity`(アイデンティティへの脅威)、`embarrassment`(きまり悪さ)、`guilt`(罪悪感)。「信頼性が損なわれる」「評判が下がる」「指標が低下」「ユーザーが離脱」「信頼を失う」「キャリアに影響」のような機能的/結果的な言い換えはこのゲートに FAIL します — 実際の B2B stakes を記述していても — これらは*結果*であり、persona が*離れたい*と思う*感じている感情*ではありません。

Q5 が persona の最も深い動機を機能的な言語だけで記述すれば、それは Discovery の契約に FAIL します:Q5 の存在意義そのものが、切替えを駆動する*感じられた恐怖/不安*を表面化することです — 純粋に機能的な結果は漸進的により良いツールで解決できますが、感じられた fear/anxiety こそが B2B buyer に組織の慣性を乗り越えて新しい契約に署名させるのです。

**合格例**(各々に標準語彙が1つ含まれる):
- ✅ 職業的アイデンティティ:「彼女は経営陣の前で無能に見えることを**恐れて(fears)**いる — このレポートが部門の信頼性を代表するから」
- ✅ 感情的動機:「彼は静かな**不安(anxiety)**を抱えている — 直属の部下に、実は数字を完全には把握していないと見抜かれることへの」
- ✅ 心理的恐怖:「彼女の最大の**畏怖(dread)**は監査人にプロセスのギャップを発見されること — 以前すでに一度警告を受けており、二度目の**恥(shame)**は人事ファイルに永久に残る」
- ✅ アイデンティティへの脅威:「外部のコンサルタントが取締役会で彼自身のチームの指標を彼より上手く説明するとき、彼は**アイデンティティへの脅威(threat to identity)**を感じる」

**不合格例**(機能的/結果的、標準語彙なし):
- ❌ 「より良いツールで効率を改善したい」(機能レベルにとどまっている)
- ❌ 「リーダーシップに対する彼女の信頼性がリスクに晒される」(結果であり、感じられた感情ではない)
- ❌ 「もしこのレポートが間違っていたら、彼女は職を失うかもしれない」(結果であって感情ではない — その可能性に対して彼女は*何を感じている*?)
- ❌ 「組織における彼の評判が損なわれる」(結果 — `embarrassment`、`shame`、または `dread` に置き換えるべき)

誠実な分析の後で persona の最も深い動機が標準語彙のいずれにも本当に対応しない場合、JTBD 品質チェックリストの Q5 項目を `❌` でマークし、理由として「Q5 は現在結果のレイヤーにとどまっている;感じられた感情を引き出すためのもう1ラウンドのインタビュー質問が必要」と書いてください — 標準語彙リストを言い換えて ✅ を作り出さないこと。

#### 競合代替品分析（必須）

ユーザーが実際に使用している代替品をリスト化：
- 少なくとも2つの名前付き既存ツール（例：Slack / Excel / 紙のフォーム / メール / 口頭連絡）
- 各ツールについて「根本的な欠陥」を説明：機能が弱いのではなく、「この欠陥がなぜ受け入れられ、未解決のまま放置されているか」（組織の慣性？切り替えコスト？経営層が気にしない？）

### 📋 ユーザーインタビュー計画テンプレート

```
## ユーザーインタビュー計画

**リサーチ目標**：[ターゲットペルソナ]が[ジョブコンテキスト]で[特定の問題]にどう対処しているかを理解する
**スクリーニング基準**：
  - 過去[X日/週]以内に[特定の行動]を経験していること
  - 除外：[適さない人 — 例：社内従業員、既知のパワーユーザー]

**コア質問（5-7問）**：
1. 最後に[問題]に直面した時、どのように対処したか手順を教えていただけますか？（行動回想）
2. そのプロセスで最もフラストレーションを感じた、または時間がかかった部分は？（ペインポイント特定）
3. 他のアプローチを試しましたか？なぜ試した/試さなかった？（現在の代替手段）
4. その部分がより良くなるとしたら、「より良い」とはどんな状態ですか？（理想の状態）
5. これはどのくらいの頻度で起きますか？最後はいつでしたか？（頻度と緊急性）
6. あなた以外に、この問題の影響を受ける人はいますか？（ステークホルダーマッピング）
7. 1-10のスケールで、この問題のあなたにとっての深刻度は？その理由は？（ペインの定量化）

**フォローアップ戦略**：
  - インタビュイーが「普段は...」と言った時 → 「具体的に前回はどうなりましたか？」と聞く
  - インタビュイーが感情に言及した時 → 「その気持ちをもう少し具体的に説明いただけますか？」と聞く
  - インタビュイーがツール/方法に言及した時 → 「そのアプローチを選んだ理由は何ですか？」と聞く

**文書化フォーマット**：
  - 逐語録または録音
  - インタビュー後24時間以内に、以下をタグ付け：重要な引用 / ペインポイント / 驚くべき発見 / 仮定との矛盾
```
