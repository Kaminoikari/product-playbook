# 阶段一：Discovery — JTBD 分析

## 1.3 JTBD（Jobs to Be Done）分析

> 「分析的单位不是消费者，而是消费者试图完成的那件工作。」— Clayton Christensen

**JTBD 三层覆盖(Hard Gate — 三层皆必填):**

每一份 JTBD 分析都必须**明确呈现三层**:**Functional**(要完成的任务)、**Emotional**(过程中/完成后想要感受的情绪)、**Social**(希望被他人看见的形象)。只产出 Functional 层是 JTBD 最常见的失误——Emotional 与 Social Job 往往才是真正的切换触发点,B2B 尤其。如果某 Persona 真的对该产品没有明确的 Emotional 或 Social Job,请用一句话明说理由——不要静默省略整列。

**JTBD 标准句型（Hard Gate — 强制三段式）：**

每一条 JTBD（不论是 Primary、Functional、Emotional、Social 任何一层）都必须写成完整的「**当 ... 我想要 ... 以便 ...**」三段式语句，三个子句缺一不可：

```
当 [情境]，我想要 [动机/工作]，以便 [成果/感受]。
```

英文输出时使用对应的标准句型：
```
When [situation], I want to [motivation], so [outcome].
```

**不合格示例**（在表格栏位中只写片段描述，缺少子句结构）：
- ❌ 「快速记下重点，避免遗忘」（缺 When；缺 so）
- ❌ 「在通勤时顺手记录」（缺 I want to；缺 so outcome）

**合格示例**（三段子句齐全）：
- ✅ 「**当**我刚读完一篇文章还记得重点时，**我想要**用 5 秒钟记下一条我觉得最值得的洞察，**以便**几周后仍能找回并串联这个想法。」

范例：正在比较房贷方案的首购族，**当**深夜不方便联络银行时，**想要**快速估算每月还款金额，**以便**向伴侣说明财务规划。

**JTBD 四种类型分析表：**

每一栏位（Persona 1 / Persona 2）必须填入完整的三段式 JTBD，不允许省略子句或只写描述性短语。

```
| JTBD 类型 | 定义 | Persona 1（必须为「当 ... 我想要 ... 以便 ...」完整句） | Persona 2（同左） |
|-----------|------|-----------|-----------|
| 功能性工作（Functional Job） | 完成特定任务或达成功能性目标 | | |
| 情感性工作（Emotional Job） | 感受或希望有什么感受 | | |
| 社交性工作（Social Job） | 希望在他人眼中呈现什么形象 | | |
| 工作情境（Job Context） | 在什么情况下需要完成这份工作 | | |
```

**JTBD 深挖五问：**
1. **根本问题**：用户表达的需求背后，真正想解决的是什么？
2. **现行限制**：哪些解法因为某些条件限制被排除在外？
3. **现行做法**：用户现在用什么方法应对？做了哪些 workaround？
4. **差距**：现行做法哪里无法令他们满意？（这个差距就是你的机会）
5. **理想解法**：如果限制消除，他们理想中的解法是什么样子？

**Teresa Torres 用户访谈最佳实践：**
- 聚焦在用户过去的**实际行为**，而不是假设性的未来行为
- 问「上一次你遇到这个问题时，你怎么做的？」而不是「你希望有什么功能？」
- 最常见错误：问假设性问题、带入解法偏见、没有追问细节

### 📝 JTBD 品质自检清单

Claude 产出 JTBD 后必须自我检查（每项必须标记 ✅ 或 ❌，❌ 项目必须说明如何改善）：
- [ ] 功能性 / 情感性 / 社交性三层**每一层**都写成「**当 ... 我想要 ... 以便 ...**」三段式完整句？（英文则为 "When ... I want to ... so ..."；任一层缺子句即标 ❌）
- [ ] 是否包含具体情境？（不是「随时随地」，而是「在深夜不方便联络银行时」）
- [ ] 是否聚焦在一个核心工作？（不是三个 Job 合并成一句）
- [ ] 是否能用来判断「这个解法有没有解决这个 Job」？
- [ ] 是否包含「现行做法」和「差距」？（差距 = 机会）
- [ ] 深挖五问的 Q5 是否**明确使用至少一个标准词汇**(`fear`、`anxiety`、`shame`、`worry`、`dread`、`self-doubt`、`sense of loss`、`threat to identity`、`embarrassment`、`guilt`)?Paraphrase 成「信誉受损」「名声下滑」这类后果性描述 FAIL 此项——它们是后果不是感受到的情绪。

**执行规则（Hard Gate）**：
- 必须逐项标记 ✅ 或 ❌，不允许保留空白 [ ] 或不说明的 ✅ 列表
- **清单必须至少出现 1 个 ❌**（见 `references/rules-quality-review.md`「强制批判」规则）。⚠️ 警告符号不能取代 ❌；外挂在清单之外的「最弱环节」备注也不能取代。若反覆审视仍觉得每项皆过，请降低标准重审，找出最该被标 ❌ 的一项并指明该如何补强
- ❌ 常见问题：三段式不完整（缺 When / I want to / so）、太抽象、太多 Job 合并、缺少情境、用产品功能替代 Job 描述、Q5 停在功能层面

### 🏢 B2B 产品专用深度要求(Hard Gate)

**Hard Gate — 任何 B2B(含 B2B2C)产品,下列三个子分析皆为必填。漏任一个即算 contract failure,不论用户有没有明确要求。** 若产品类型不明确,请先问一个 clarification 问题;不要默默假设为 B2C。

#### 组织层级 Job 分析(Hard Gate — 至少覆盖 2 层)

B2B JTBD 分析若全停留在个人使用者层级,FAIL 此 gate。组织层级的 Job(合规稽核、跨部门审批流程、成本控制、人力政策对齐、稽核轨迹完整性)是超越任何单一使用者日常任务的需求,在 B2B 切换决策中经常占主导。下表必须产出,且 3 层中至少 2 层必须含具 B2B 特性的 Job(不是空泛的生产力陈述)。

| 层级 | 说明 | 范例 |
|------|------|------|
| **Strategic Job** | 组织/管理层的跨部门需求 | 合规稽查、成本控制、人力资源优化 |
| **Operational Job** | 流程/部门主管的协调需求 | 审批流程管理、跨部门资讯同步 |
| **Task Job** | 个别使用者的日常操作需求 | 填写表单、查询状态、汇出报表 |

#### 买方(Buyer)vs 使用者(User)分析(Hard Gate)

B2B 产品的买方(签合约、掌预算)和日常使用者(每天接触产品)几乎都是两个角色、**对应不同的 Job**。把他们当成单一 Persona 是 B2B Discovery 最常见的失误。Hard Gate 规则:

- 若 buyer ≠ user(B2B 预设假设),请产出**两个独立的 Persona+JTBD 区块**:一个给 Buyer(ROI 说明、风险降低、合规、供应商整并、稽核就绪),一个给 User(效率、减错、日常使用情境)。并交叉连结:标出买方的 Job 何处依赖使用者的 Job(例如「买方的合规 Job 取决于使用者真的每周填报,而不是月底补登」)。
- 若 buyer = user(少数例外,例如创办人主导工具),请用一句话明确说明为何此特定场景下决策者即日常使用者——不要默默假设。
- 不合格范例:只产出一个 Persona(「HR 经理」),把预算决策权与日常填表硬塞进同一个模糊原型。这把两个不同的 Job 压成一个含糊角色,分析无法驱动产品决策。

#### 深挖五问 B2B 强化版(Hard Gate)

**Hard Gate — Q5 必须明确使用下列标准词汇清单至少一个词**:`fear`(恐惧)、`anxiety`(焦虑)、`shame`(羞愧)、`worry`(担忧)、`dread`(畏惧)、`self-doubt`(自我怀疑)、`sense of loss`(失落感)、`threat to identity`(身份威胁)、`embarrassment`(尴尬)、`guilt`(罪恶感)。Paraphrase 成「信誉受损」「名声下滑」「指标下降」「用户流失」「失去信任」「影响职涯」这类功能性/后果性描述 FAIL 此 gate,即使描述的是真实 B2B stakes——这些是*后果*,不是 persona 想要*离开*的*真实感受*。

Q5 若只用功能性语言描述 persona 最深的动机,就 FAIL 了 Discovery 的契约:Q5 整个存在的目的就是表面化驱动切换的*感受到的恐惧/焦虑*,因为纯功能性结果可以靠渐进更好的工具解决,但被感受到的 fear/anxiety 才是让 B2B buyer 越过组织惯性、签下新合约的关键。

**合格范例**(每个都含一个标准词汇):
- ✅ 职业认同:「她**害怕(fears)**在高层面前出糗,因为这份报表代表她部门的专业度」
- ✅ 情感动机:「他带着一种无声的**焦虑(anxiety)**——怕被直属下属发现自己其实没掌握数字」
- ✅ 心理恐惧:「她最大的**畏惧(dread)**是被稽核单位抓到流程漏洞——上次已被警告过一次,二度发生的**羞愧(shame)**会永远留在她的人事档案」
- ✅ 身份威胁:「他感受到**身份威胁(threat to identity)**——当外部顾问在董事会上比他更会解读他自己团队的指标」

**不合格范例**(功能性/后果性,没有标准词汇):
- ❌ 「他需要一个更好的工具来提高效率」(停留在功能层面)
- ❌ 「她在高层那边的信誉会受损」(后果,不是感受到的情绪)
- ❌ 「如果这份报表错了她可能会丢工作」(结果,不是感受——对这个可能性她*感受*到什么?)
- ❌ 「他在组织内的名声会受影响」(后果——应改用 `embarrassment`、`shame` 或 `dread`)

如果经诚实分析后 persona 最深的动机真的不对应任何标准词汇,请在 JTBD 品质自检清单把 Q5 标 `❌`,理由写「Q5 目前停在后果层,需要再一轮访谈去问出感受到的情绪」——不要借由 paraphrase 标准词汇清单来生出一个 ✅。

#### 竞品替代品分析（必填）

列出目前使用者实际使用的替代方案：
- 至少 2 个具名现行工具（如 Line/Excel/纸本/Email/口头沟通）
- 每个工具必须说明其「根本缺陷」：不是功能差，而是「为什么这个缺陷被接受却没被解决」（组织惯性？切换成本？上级不在意？）

### 📋 用户访谈计划模板

```
## 用户访谈计划

**研究目标**：了解 [目标 Persona] 在 [Job Context] 中的 [具体问题]
**受访者筛选条件**：
  - 必须在过去 [X 天/周] 内有过 [具体行为]
  - 排除：[哪些人不适合，例如内部员工、已知的忠实用户]

**核心问题（5-7 题）**：
1. 上一次你遇到 [问题] 时，可以带我走一遍你是怎么处理的吗？（行为回溯）
2. 在那个过程中，最让你困扰/花最多时间的是哪个环节？（痛点定位）
3. 你有试过其他方法吗？为什么用/不用？（现行替代方案）
4. 如果那个环节可以变得更好，「好」对你来说是什么样子？（理想状态）
5. 这件事多久会发生一次？最近一次是什么时候？（频率和急迫性）
6. 除了你以外，还有谁会受到这个问题的影响？（利害关系人）
7. 如果要用 1-10 分评量这个问题的严重程度，你会打几分？为什么？（量化痛感）

**追问策略**：
  - 当受访者说「通常我会...」→ 追问「上一次具体是什么情况？」
  - 当受访者提到情绪 → 追问「那个感觉具体是什么？」
  - 当受访者提到某个工具/方法 → 追问「是什么让你选择这个方式？」

**记录格式**：
  - 逐字稿 or 录音
  - 访后 24 小时内标记：关键引言 / 痛点 / 惊喜发现 / 与假设不符之处
```
