# 品質審查規則

> 每個步驟完成時載入。

## 審查流程

每個步驟產出後：
1. 對應步驟的檢查清單，逐項標 ✅ 或 ❌。每個 ❌ 必須說明：內容缺口 / 下游影響 / 改善方向。
2. **至少 1 個 ❌（Hard Gate）**：⚠️ 不能替代 ❌；不可外掛「最弱環節」旁註；❌ 必須是實質內容缺口，非排版/字數。若反覆審視覺得全 ✅ → 降低標準重審。任何規劃產出必有最弱環節。
3. 格式：`📝 品質自檢：` 然後逐項 `- ✅/❌ 項目 → 缺口 / 影響 / 改善`。

自我檢查的檢查：若清單無任何 ❌ → 回到步驟 2 重做。

## 各框架檢查清單

**Persona**：1) 基於用途/動機而非人口統計；2) MECE；3) 核心 vs 次要 TA 明確；4) 痛點來自真實觀察/合理推論；5)「現行做法 + 理由」具體到可識別 workaround。

**JTBD**：1) 情境具體（非「隨時隨地」）；2) 單一核心 job；3) 功能/情感/社交皆具備；4) 可用來評估解法；5)「現行做法 + 差距」明確；6) 深挖五問 Q5 觸及情感/認同/恐懼。

**Positioning（April Dunford）**：1) 競爭替代品來自用戶視角；2) 獨特屬性是競對做不到的；3) 價值用用戶語言而非產品語言；4) 目標市場具體到能找到人；5) 五個要素邏輯一致。

**HMW**：1) 約束條件明確；2) 解法空間夠寬；3) 對應到 JTBD/痛點；4) 團隊能直接開始發想。

**PR-FAQ**：1) 標題用戶視角（「用戶能做到 X」）；2) 第一段 10 秒內傳達「為什麼重要」；3) 痛點來自真實場景；4) 解法段以用戶感受開頭；5) 用戶引言像真人說的話；6) FAQ 包含對比現有工具的尖銳質疑。

**North Star**：1) 反映用戶獲得的價值（非營收/DAU）；2) 可持續增長；3) 團隊看到指標知道該做什麼；4) 若可操弄需護欄；5) B2B 反映組織層級價值。

**Aha Moment**：1) 具體可追蹤的行為；2) 對應 JTBD 功能性 job；3) 到達時間合理（B2C：首次使用；B2B：試用期）；4) Onboarding 可設計引導。

**安全性**（完整：`08-security-checklist.md`）：1) 認證方式明確選定；2) 至少 3 個安全 headers 已規劃；3) Rate limit 針對產品特性調整非套模板；4) `.gitignore` 涵蓋所有敏感檔案。

**文件匯出**（完整：`rules-export-document.md`）：1) HTML 中無殘留 Markdown 語法；2) 表格列數欄數與原始一致。

## 跨步驟一致性審查（流程結束時）

詳細：`rules-end-of-flow.md`。

| # | 維度 | 驗證問題 |
|---|------|---------|
| 1 | 目標用戶 | JTBD、Positioning、PR-FAQ 是否指向同一群人？ |
| 2 | 核心問題 | PR-FAQ 是否針對 JTBD 的問題？MVP 是否解決？ |
| 3 | 解法 ↔ 範圍 | 選出的解法是否與 MVP 範圍一致？ |
| 4 | 指標 ↔ 價值 | North Star 是否衡量 JTBD 成果？ |
| 5 | 風險時效性 | Pre-mortem 風險對最終解法是否仍相關？ |
