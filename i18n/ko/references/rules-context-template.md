# 📦 제품 컨텍스트 — 템플릿 및 상세 UX 스크립트

> 지연 로드 레퍼런스. `rules-context.md` §8의 트리거 표에 따라 트리거됨. 일상적인 세션 시작에 필요하지 않은 상세 YAML/markdown 형식과 UX 스크립트만 포함.

## Bootstrap (시나리오 2 전용)

사용자가 **기능 확장** 또는 **리비전 모드**에 진입하지만 `.product-context.md`가 없는 경우, S1 앞에 "Step 0"을 삽입.

**표시:**
```
📦 이 프로젝트에서 제품 기획 도구를 처음 사용하시는군요. 후속 플로우를 더 효율적으로 만들기 위해,
기본적인 제품 정보를 먼저 수집하겠습니다 (약 2-3분). 향후 사용을 위해 자동 저장됩니다.
```

### 점진적 수집 (모든 질문을 한 번에 하지 마세요)

**라운드 1 (모든 모드에 필수):**
- 제품의 이름은 무엇인가요?
- 한 문장으로 무엇을 하는지 설명해 주세요.
- 제품 유형은? (B2C / B2B / B2B2C / 내부 도구)

**라운드 2 (기능 확장에 필수, 리비전에 선택):**
- 어떤 기술 스택을 사용하나요? (언어, 프레임워크, 데이터베이스, 인프라)
- 주요 모듈이나 서비스는 무엇인가요?

**라운드 3 (리비전에 필수, 기능 확장에 선택):**
- DAU/MAU나 리텐션율 데이터가 있나요?
- 가장 흔한 사용자 피드백이나 불만은 무엇인가요?
- 알려진 보안 이슈나 기술 부채가 있나요?

### 기술 스택 자동 감지

Bootstrap은 프로젝트 파일을 읽을 수 있음 (읽기 전용, Hard Gate 위반 아님):

| 파일 | 감지 내용 |
|------|----------|
| `package.json` | Node.js 생태계, 프레임워크, 의존성 |
| `Cargo.toml` | Rust |
| `go.mod` | Go |
| `requirements.txt` / `pyproject.toml` | Python |
| `Dockerfile` / `docker-compose.yml` | 컨테이너화 아키텍처 |
| 프로젝트 루트 구조 (`src/`, `app/`, `lib/` 등) | 모듈 추론 |

확인 스타일:
```
프로젝트가 다음을 사용하는 것으로 감지되었습니다:
- 기술 스택: Next.js 14 + TypeScript + PostgreSQL + Redis
- 주요 모듈: auth/, billing/, dashboard/, api/
맞나요? 추가하거나 수정할 것이 있나요?
```

사용자가 확인한 후에만 쓰기.

### Bootstrap → S1 순서 (Hard Gate — Bootstrap은 플로우를 차단하지 않음)

- **기본 동작**: Bootstrap과 S1은 **같은 턴** 안에서 S0 → S1 순서로 실행되어야 합니다. 정지 지점은 **S1 완료 후**에 고정되며, S0/S1 사이가 아닙니다.
- **사용자 메시지에 필요한 필드가 이미 제공된 경우** → 표로 확인하고 S1으로 진행.
- **필드가 누락된 경우** → 같은 턴 안에서 알려진/미수집 표를 표면화하고, 플레이스홀더로 S1에 진입하며, 미수집을 S1 확인 질문에 묶음.
- **금지**: Round 1 답변을 기다리기 위해 S0과 S1 사이에 일시 정지. 사용자 입력을 기다리는 동안 S1이 `⬜ pending`을 표시하면, 이 규칙을 위반한 것입니다.

Bootstrap 후: `.product-context.md`에 쓰기 (플레이스홀더라도), 같은 턴 안에서 S1 진입.

## 부분 컨텍스트 UX (시나리오 3)

```
📦 이전 [N]회 기획 세션의 기록이 있습니다:
- 기술 스택: [Decision History에서 병합된 알려진 스택]
- 이전에 수정된 모듈: [Decision History에서 병합된 영향받은 모듈]
- 핵심 제품 전략은 아직 기록되지 않았습니다.

어떻게 하시겠습니까:
  1️⃣ 바로 시작 (알려진 정보 사용, 전략 섹션 건너뛰기)
  2️⃣ 전략 정보 먼저 보완 (JTBD, 포지셔닝, North Star Metric)
  3️⃣ 이 정보가 맞지 않아요 — 수정하겠습니다
```

**자동 재구축 시도**: Decision History 스캔, `영향받은 모듈`, `범위`, `핵심 결정`에서 반복되는 제품명, 기술 스택, 모듈명 추출. `Architecture & Tech Stack`에 자동 입력. `<!-- inferred from decision history -->`로 표시.

## 충돌 UX (코드베이스 vs 컨텍스트)

```
⚠️ 불일치가 감지되었습니다:
- 컨텍스트 기록: [컨텍스트의 값]
- 프로젝트 코드베이스: [코드에서 감지된 값]
어느 것이 맞나요?
  1️⃣ 코드베이스를 진실의 원천으로 사용 (컨텍스트 업데이트)
  2️⃣ 컨텍스트를 진실의 원천으로 사용 (마이그레이션 중일 수 있음)
  3️⃣ 둘 다 불완전 — 설명하겠습니다
```

- 자동 덮어쓰기 금지 — 사용자가 결정
- 마이그레이션 중인 경우: Architecture에 `[Migrating] React → Vue 3`로 주석
- 충돌을 Decision History에 기록
