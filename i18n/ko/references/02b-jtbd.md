# 1단계: 디스커버리 — JTBD 분석

## 1.3 JTBD (Jobs to Be Done) 분석

> "분석의 단위는 소비자가 아니라, 소비자가 완수하려는 과업(Job)입니다." — Clayton Christensen

**JTBD 3계층 커버리지(Hard Gate — 3계층 모두 필수):**

모든 JTBD 분석은 **3계층을 명시적으로 표면화**해야 합니다: **Functional**(완수할 과업), **Emotional**(과정 중/완료 후 어떻게 느끼고 싶은지), **Social**(타인에게 어떻게 인식되고 싶은지). Functional 계층만 생성하는 것이 JTBD 에서 가장 흔한 실패입니다 — Emotional 과 Social Job 이 실제 전환 트리거인 경우가 많고, B2B 에서는 특히 그렇습니다. 만약 어떤 Persona 가 제품에 대해 정말로 의미 있는 Emotional 또는 Social Job 이 없다면, 침묵하며 행을 누락하지 말고 한 문장의 reasoning 으로 명시하세요.

**JTBD 표준 구문(Hard Gate — 3절 구조 강제):**

모든 JTBD 문(Primary, Functional, Emotional, Social 어떤 계층이든)은 **"~할 때, ~하고 싶다, 그래서 ~"** 3절 구조의 완전한 문장으로 작성해야 합니다. 세 절 중 어느 하나라도 빠지면 안 됩니다:

```
[상황]할 때, [동기/과업]하고 싶다, 그래서 [결과/감정]을 얻는다.
```

영어 출력 시에는 대응하는 표준 구문을 사용:
```
When [situation], I want to [motivation], so [outcome].
```

**불합격 예시**(표 셀에 단편적 설명만 있고 절 구조가 누락):
- ❌ "요점을 빠르게 메모한다"(When 누락; so 누락)
- ❌ "출퇴근 중에 떠오를 때 기록한다"(I want to 누락; so outcome 누락)

**합격 예시**(세 절 모두 갖춤):
- ✅ "**기사를 막 읽고 요점이 아직 머릿속에 남아 있을 때**, 5초 안에 가장 가치 있는 인사이트 하나를 기록**하고 싶다**. **그래서** 몇 주 후에도 찾아내어 새로운 아이디어와 연결할 수 있다."

예시: 모기지 옵션을 비교하는 첫 주택 구매자가, **은행에 연락할 수 없는 늦은 밤**에 월 상환액을 **빠르게 추산하고 싶다**, **그래서** 배우자에게 재정 계획을 설명할 수 있다.

**JTBD 4가지 유형 분석표:**

각 칸(Persona 1 / Persona 2)에는 완전한 3절 구조의 JTBD를 작성하세요. 절을 생략한 서술형 문구는 허용되지 않습니다.

```
| JTBD 유형 | 정의 | Persona 1(「~할 때 / ~하고 싶다 / 그래서 ~」 완전문 필수) | Persona 2(동일) |
|-----------|------|-----------|-----------|
| 기능적 Job | 특정 과업을 완수하거나 기능적 목표를 달성 | | |
| 감정적 Job | 어떤 감정을 느끼거나 느끼고 싶은지 | | |
| 사회적 Job | 다른 사람들에게 어떻게 인식되고 싶은지 | | |
| Job 맥락 | 어떤 상황에서 이 과업을 완수해야 하는지 | | |
```

**JTBD 심층 5가지 질문:**
1. **근본 문제**: 사용자가 표현하는 니즈 뒤에, 실제로 해결하려는 것은 무엇인가?
2. **현재 제약**: 어떤 제약 때문에 어떤 솔루션이 배제되었는가?
3. **현재 우회 방법**: 사용자가 현재 어떻게 대처하고 있는가? 어떤 우회 방법을 만들었는가?
4. **갭**: 현재 우회 방법이 부족한 부분은 어디인가? (이 갭이 당신의 기회입니다)
5. **이상적 솔루션**: 제약이 없다면, 이상적인 솔루션은 어떤 모습일까?

**Teresa Torres 사용자 인터뷰 모범 사례:**
- 사용자의 **실제 과거 행동**에 집중하고, 가상의 미래 행동이 아닌
- "지난번 이 문제에 부딪혔을 때, 어떻게 하셨나요?"라고 질문하고, "어떤 기능을 원하세요?"가 아닌
- 가장 흔한 실수: 가상 질문, 솔루션 편향 도입, 세부사항 추적 부족

### 📝 JTBD 품질 체크리스트

Claude는 JTBD 산출물 작성 후 자체 점검해야 합니다 (각 항목은 ✅ 또는 ❌로 표시; ❌ 항목은 개선 방법 포함):
- [ ] 기능적 / 감정적 / 사회적 **세 계층 모두**가 "~할 때 / ~하고 싶다 / 그래서 ~"(영어로는 "When ... I want to ... so ...") 완전한 3절 구조로 작성되었는가? (어느 한 계층이라도 절이 빠지면 ❌)
- [ ] 구체적인 맥락이 포함되어 있는가? ("언제 어디서나"가 아닌 — "은행에 연락할 수 없는 늦은 밤")
- [ ] 단일 핵심 Job에 집중하는가? (한 문장에 세 가지 Job이 섞여 있지 않은가)
- [ ] "이 솔루션이 실제로 이 Job을 해결하는가?"를 평가하는 데 사용할 수 있는가?
- [ ] "현재 우회 방법"과 "갭"이 포함되어 있는가? (갭 = 기회)
- [ ] 심층 Q5 가 **표준 어휘 중 최소 하나를 명시적으로 사용**하는가 (`fear`, `anxiety`, `shame`, `worry`, `dread`, `self-doubt`, `sense of loss`, `threat to identity`, `embarrassment`, `guilt`)? "신뢰성이 손상", "평판이 떨어짐" 같은 결과적 패러프레이즈는 이 항목에 FAIL — 그것들은 결과이지 느낀 감정이 아님.

**실행 규칙 (하드 게이트):**
- 각 항목을 반드시 ✅ 또는 ❌로 표시 — 빈 [ ]이나 설명 없는 ✅ 목록은 허용되지 않음
- **체크리스트에는 반드시 1개 이상의 ❌가 있어야 함**(`references/rules-quality-review.md`「강제 비판」규칙 참조). ⚠️ 경고 마크는 ❌를 대체할 수 없으며, 체크리스트 외부의 「가장 약한 부분」 메모도 대체할 수 없음. 반복해서 검토해도 모든 항목이 통과로 느껴진다면 기준을 낮추어 재검토하고, ❌를 표시할 항목을 하나 찾아 강화 방법을 명시할 것
- ❌ 흔한 문제: 3절 구조 누락 (When / I want to / so 중 하나 누락), 너무 추상적, 여러 Job 혼합, 맥락 누락, 제품 기능으로 Job 설명 대체, Q5가 기능 수준에 머무름

### 🏢 B2B 제품 심층 분석 요구사항 (Hard Gate)

**Hard Gate — 모든 B2B (B2B2C 포함) 제품에 대해, 아래 3개 하위 분석은 모두 필수입니다. 사용자가 명시적으로 요청하지 않았더라도 어느 하나라도 빠지면 contract failure 입니다.** 제품 유형이 불명확한 경우 먼저 한 가지 명료화 질문을 하세요 — 묵시적으로 B2C 로 가정하지 마세요.

#### 조직 수준 Job 분석 (Hard Gate — 최소 2개 수준 포함)

B2B JTBD 분석이 개별 사용자 수준에만 머무르면 이 gate 에 FAIL. 조직 수준의 Job (규정 준수 감사, 부서 간 결재 워크플로우, 비용 통제, 인력 정책 정렬, 감사 추적 완전성) 은 개별 사용자의 일상 과업을 초월하는 니즈이며, B2B 전환 결정에서 일상적으로 지배적입니다. 아래 표는 반드시 생성되어야 하며, 3개 수준 중 최소 2개는 B2B 특유의 Job (모호한 생산성 진술이 아닌) 을 포함해야 합니다.

| 수준 | 설명 | 예시 |
|------|------|------|
| **전략적 Job** | 조직/경영 수준의 부서 간 니즈 | 규정 준수 감사, 비용 통제, 인력 최적화 |
| **운영적 Job** | 프로세스/부서 관리자 수준의 조율 니즈 | 결재 워크플로우 관리, 팀 간 정보 동기화 |
| **실무적 Job** | 개별 사용자의 일상 업무 니즈 | 양식 작성, 상태 확인, 보고서 내보내기 |

#### 구매자(Buyer) vs 사용자(User) 분석 (Hard Gate)

B2B 제품의 구매자 (계약 체결, 예산 관리) 와 일상 사용자 (매일 제품 사용) 는 거의 항상 두 개의 역할이며, **서로 다른 Job 에 대응**합니다. 이들을 단일 Persona 로 취급하는 것은 B2B 디스커버리에서 가장 흔한 실패입니다. Hard Gate 규칙:

- buyer ≠ user 인 경우 (B2B 기본 가정), **두 개의 별개 Persona+JTBD 블록**을 생성: 하나는 Buyer 용 (ROI 정당화, 리스크 감소, 컴플라이언스, 벤더 통합, 감사 준비), 하나는 User 용 (효율, 오류 감소, 일상 사용 맥락). 그리고 크로스링크: Buyer 의 Job 이 User 의 Job 에 어디서 의존하는지 표기 (예: "Buyer 의 컴플라이언스 Job 은 월말 일괄 작성이 아닌, User 가 매주 실제로 기록하느냐에 달려 있음").
- buyer = user 인 경우 (예외적 — 보통 창업자 주도 도구), 왜 이 특정 시나리오에서 의사결정자가 일상 사용자이기도 한지 한 문장으로 명시 — 묵시적으로 가정하지 마세요.
- 불합격 예: 하나의 Persona ("HR 매니저") 만 생성하여 예산 의사결정 권한과 일상 양식 작성을 하나의 모호한 아키타입에 욱여넣음. 이는 두 개의 다른 Job 을 하나의 흐릿한 역할로 압축하며, 분석이 제품 결정을 이끌어낼 수 없게 됩니다.

#### 심층 5가지 질문 — B2B 강화 버전 (Hard Gate)

**Hard Gate — Q5 는 다음 표준 어휘 목록에서 최소 하나를 명시적으로 사용해야 합니다**: `fear`(두려움), `anxiety`(불안), `shame`(수치심), `worry`(걱정), `dread`(공포), `self-doubt`(자기 의심), `sense of loss`(상실감), `threat to identity`(정체성 위협), `embarrassment`(당혹감), `guilt`(죄책감). "신뢰성이 손상됨", "평판이 떨어짐", "지표가 하락", "사용자가 이탈", "신뢰를 잃음", "커리어에 영향" 같은 기능적/결과적 패러프레이즈는 이 gate 에 FAIL — 실제 B2B stakes 를 기술하더라도 — 이들은 *결과*이지, persona 가 *벗어나고자 하는* *느낀 감정*이 아닙니다.

Q5 가 persona 의 가장 깊은 동기를 기능적 언어로만 기술하면 Discovery 계약에 FAIL: Q5 의 존재 이유 자체가 전환을 이끄는 *느낀 두려움/불안*을 표면화하는 것입니다 — 순수 기능적 결과는 점진적으로 더 나은 도구로 해결될 수 있지만, 느낀 fear/anxiety 가 B2B buyer 로 하여금 조직적 관성을 넘어 새 계약에 서명하게 만드는 것입니다.

**합격 예시** (각각 하나의 표준 어휘 포함):
- ✅ 직업적 정체성: "그녀는 리더십 앞에서 무능해 보이는 것을 **두려워합니다(fears)** — 이 보고서가 그녀 부서의 신뢰성을 대표하기 때문에"
- ✅ 감정적 동기: "그는 조용한 **불안(anxiety)**을 안고 있습니다 — 직속 부하들이 그가 실제로는 숫자를 완전히 파악하지 못하고 있다는 것을 알아차릴까 봐"
- ✅ 심리적 공포: "그녀의 가장 큰 **공포(dread)**는 감사관이 프로세스 갭을 발견하는 것 — 이미 한 번 경고를 받았고, 두 번째 발생 시의 **수치심(shame)**은 인사 파일에 영구히 남을 것"
- ✅ 정체성 위협: "외부 컨설턴트가 이사회에서 그 자신의 팀 지표를 그보다 더 잘 설명할 때, 그는 **정체성 위협(threat to identity)**을 느낍니다"

**불합격 예시** (기능적/결과적, 표준 어휘 없음):
- ❌ "그는 효율을 개선하기 위해 더 나은 도구가 필요합니다" (기능 수준에 머무름)
- ❌ "리더십에 대한 그녀의 신뢰성이 위험에 처합니다" (결과, 느낀 감정이 아님)
- ❌ "이 보고서가 틀리면 그녀는 일자리를 잃을 수 있습니다" (결과이지 감정이 아님 — 그 가능성에 대해 그녀는 *무엇을 느낍니까*?)
- ❌ "조직 내 그의 평판이 영향을 받습니다" (결과 — `embarrassment`, `shame`, 또는 `dread` 로 대체해야 함)

정직한 분석 후 persona 의 가장 깊은 동기가 정말로 어떤 표준 어휘에도 해당하지 않는다면, JTBD 품질 체크리스트의 Q5 항목을 `❌` 로 표시하고 이유를 "Q5 가 현재 결과 계층에 머물러 있음; 느낀 감정을 끌어낼 한 차례 더의 인터뷰 질문이 필요" 로 작성 — 표준 어휘 목록을 패러프레이즈해서 ✅ 을 만들어내지 마세요.

#### 경쟁 대안 분석 (필수)

사용자가 현재 실제로 사용하고 있는 대안을 나열하세요:
- 최소 2개의 구체적인 기존 도구 (예: Slack / Excel / 종이 양식 / 이메일 / 구두 소통)
- 각 도구에 대해 "근본적 결함"을 설명: 기능이 약한 것이 아닌, "왜 이 결함이 수용되고 미해결 상태인지" (조직적 관성? 전환 비용? 리더십이 관심 없음?)

### 📋 사용자 인터뷰 계획 템플릿

```
## 사용자 인터뷰 계획

**리서치 목표**: [타겟 Persona]가 [Job 맥락]에서 [특정 문제]를 어떻게 처리하는지 이해
**스크리닝 기준**:
  - 지난 [X일/주] 이내에 [특정 행동]을 경험한 사람이어야 함
  - 제외: [적합하지 않은 사람 — 예: 내부 직원, 알려진 파워 유저]

**핵심 질문 (5-7개)**:
1. 지난번 [문제]에 부딪혔을 때, 어떻게 처리하셨는지 과정을 알려주실 수 있나요? (행동 회상)
2. 그 과정에서 가장 답답하거나 시간이 많이 걸린 부분은 무엇이었나요? (페인포인트 식별)
3. 다른 방법을 시도해 보셨나요? 왜 혹은 왜 안 하셨나요? (현재 대안)
4. 그 부분이 더 나아진다면, "더 나은" 상태란 어떤 모습일까요? (이상적 상태)
5. 이런 일이 얼마나 자주 발생하나요? 마지막으로 언제였나요? (빈도와 긴급성)
6. 당신 외에 이 문제의 영향을 받는 사람이 또 있나요? (이해관계자 매핑)
7. 1-10점 척도로, 이 문제가 얼마나 심각한가요? 왜 그렇게 생각하시나요? (페인 정량화)

**후속 전략**:
  - 인터뷰 대상자가 "보통은..."이라고 말할 때 → "지난번에 구체적으로 어떤 일이 있었나요?" 질문
  - 인터뷰 대상자가 감정을 언급할 때 → "그 감정을 좀 더 구체적으로 설명해 주실 수 있나요?" 질문
  - 인터뷰 대상자가 도구/방법을 언급할 때 → "그 방법을 선택하게 된 이유가 무엇인가요?" 질문

**기록 형식**:
  - 축어 녹취 또는 녹음
  - 인터뷰 후 24시간 이내에 태그: 핵심 인용문 / 페인포인트 / 놀라운 발견 / 가정에 반하는 내용
```
